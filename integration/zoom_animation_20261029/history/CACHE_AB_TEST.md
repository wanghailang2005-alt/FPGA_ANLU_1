# 源缓存 A/B 对照板测

> 本记录中的未带链接的相对路径以 `zoom_animation` 工程根目录为准。

2026-10-29。用户反馈：原尺寸静态图片在按 1000/K3 之前已经出现短横线和杂色，动画运行但显示不理想。原 `ZOOM_ANIMATION_20261029.bit` 标记 **BOARD FAIL**，已连同源码和报告备份至 `evidence/board_fail_20261029`。本轮经用户“开始 A”批准，直接修改现有 zoom_animation 中的诊断入口，不重写动画或插值算法。

## 先测试这两份

| bit | 编译参数 | 行为 |
|---|---|---|
| `ZOOM_DIAG_A_CACHE_OFF_20261029.bit` | `SOURCE_CACHE_ENABLE=0` | 原静态加载／显示保留；源缓存不上传、不占用 SDRAM，上传接受固定为 1、缓存有效固定为 0，因此不运行缓存动画。缩放设置仍走原静态重载。 |
| `ZOOM_DIAG_B_CACHE_ON_20261029.bit` | `SOURCE_CACHE_ENABLE=1` | 保留当前源缓存和动画行为，增加与 A 相同的观察计数。 |

1. 保持同一 TF 卡、HDMI 连接和显示器。下载 A，按 K1，SW4..SW1=`0000`。
2. 用 K2 选择原来有噪点的同一张草莓，等待装载结束后观察 5 秒。**先不要按 1000/K3。** 记录图片区域、白背景、上下／左右黑边是否有噪点，是否持续变化。
3. 下载 B，再按 K1，保持 `0000`，选择完全相同的图片，重复观察。两次都从复位开始，避免把不同缩放状态混在一起。
4. 若有噪点，SW 拨到 `1111`，不按 K3，给数码管拍约 5 秒视频。该页只显示诊断，不重载图片。
5. 静态对照完成后，B 才可另外测试 1000/K3 动画。A 的缓存动画被旁路，不用用动画是否出现来判断 A 成败。

反馈只需：**A 静态干净／有噪点，B 静态干净／有噪点**，加上数码管视频。优先看静态对照。

## 数码管页

在 SW=`1111` 下每秒轮换一次，共三页。扫描方向可能导致照片上的顺序与下面逻辑顺序相反，直接提供照片／视频即可，不需要手工倒序。

| 逻辑显示 | 内容 |
|---|---|
| `F A ff pp`／`F b ff pp` | A＝旁路，b＝开启；ff 为异常标志，pp 为当前未返回读请求数量的低 8 位 |
| `1 A nnnn`／`1 b nnnn` | 自复位以来已发出的读请求数量，低 16 位、十六进制 |
| `2 A nnnn`／`2 b nnnn` | 自复位以来收到的读返回数量，低 16 位、十六进制 |

计数持续运行并会回绕；请求页和返回页不是同一时刻的快照，不能直接用两张页面的数值相减判断丢字。`pp=00` 也可能是 256 等数的截断值。异常标志中，新增存储探针的五项为复位清除的 sticky 记录；原写 FIFO／视频状态保留各自原有清除语义。

ff 的位从高到低为：缓存 FIFO 错误、意外读返回、尚有未返回数据时切换访问权、同拍读写命令冲突、未返回计数溢出、目标 FIFO 清零期间写入、目标 FIFO 写溢出、当前／前一视频帧读欠载。上电首帧可能存在历史读欠载，需等待稳定后结合原状态与照片判断；不能把单一标志直接当作噪点根因。

观察探针的输入先统一寄存，计数／标志通过现有握手邮箱到系统时钟域；输出仅用于数码管，不反向控制存储、FIFO、RGB、DE、HS 或 VS。

## 已验证与未验证

- 理想存储模型下，两配置各完成两次静态装载、614400 个目标像素及对应视频读出比对。A 辅助源缓存写入为 0，B 为 153600 字；新增观察标志均为 0。
- 观察探针自检覆盖请求／返回计数、排空后的正常交接、带未返回数据的异常交接、意外返回、命令冲突和复位。
- 厂商加密控制器可以正常由 ModelSim 加载。最小控制测试中，16 个请求对应 16 次返回，首字延迟和末字尾延迟均为 11 个内存周期，12 个请求在 busy 已经为高时仍获得后续返回。因此 busy 不能未经接口确认就当作通用逐字 ready；该测试尚未覆盖所有访问模式。
- 安装包的 EG_PHY_SDRAM_2M_32 是空壳接口。连接它的数据读回为高阻，已如实保留失败日志 `sim/vendor_controller.log`。`vendor_protocol.log` 与 `vendor_off.log`／`vendor_on.log` **仅检查控制流，不验证存储内容或物理时序**。
- 实际控制器静态流测试包含刷新、原 DMA 和源缓存上传；A/B 控制流计数／归属及 FIFO 欠载检查通过。B 一次辅助占用最长 376 个 125MHz 周期（约 3.008μs）。实际板端数据完整性仍待本轮 A/B 对照。
- 两配置分别检查最终布局布线、bit 时间和哈希；结果见 `evidence/cache_compare_20261029/A/summary.json`、`B/summary.json`。PLL、厂商 IP、SDC、ADC、插值算式、帧调度和原存储仲裁状态机内容不改。

A/B 重新实现会改变物理布局布线，因此 A 干净而 B 花屏能缩小到新增缓存活动／实现影响，但不能单凭一次结果断言某个 RTL 表达式就是根因。如果两版都干净，也不能把原失败记录改成已修复，需要结合重复测试判断物理裕量。

## 源码与构建

最终对照结果：A setup +0.104ns、hold +0.011ns；B setup +0.072ns、hold +0.003ns。A SHA256 为 `cba1323534469ceb7965e52ae5d6f7fa2de7374d2fe4537b5484e814241ef4c1`，B 为 `2b9d8f97ab2d0303cf8fecaee273266285c559ce48f04c33123c2c312083d379`。

B 默认布局首次实现 setup −0.396ns，失败报告保存在 `B_seed0_timing_fail`，未作为发布 bit。B 最终仅更换 place seed=1，通过后收集；未修改原静态缩放 RTL 或时序例外。A 使用默认布局参数。A/B 源码快照已逐字核验，除 SOURCE_CACHE_ENABLE 为 0／1 外相同。

顶层 `SOURCE_CACHE_ENABLE` 为编译参数，源码最终默认 1。编译 A 时设为 0，编译 B 时设为 1，先执行 syn_1 再执行 phy_1 中现有 build_td.tcl，随后执行 `diagnostic_collect.py A` 或 `B`。两份编译时顶层与探针源码快照在各自 `source_snapshot` 内，清单包含全部源码哈希。

旧 `collect.py` 已加保护，避免将诊断 bit 覆盖为原动画版文件名。本次没有写 TF 卡、下载开发板、修改厂商加密 IP、PLL、引脚或时序例外；后续修复要依据本轮板测结果另行选择。
