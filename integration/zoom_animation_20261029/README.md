# 连续缩放及缓存诊断归档（2026-10-29）

此包记录从已板测 `zoom_black2` 继续开发的双线性缩放、缓存动画、故障诊断及板测反馈。用户最后反馈：烧录 `ZOOM_CACHE_CHECK_20261029.bit` 后所测缩放全部正常；反馈未明确是否再次覆盖奇数宽图片，因此保留先前奇数宽噪点记录。

## 使用和行为

K1 复位，K2 切图，K4 轮播；SW4..SW1=`0111` + K3 切换最近邻三档，`1000` + K3 切换双线性三档并执行连续动画。三档为原尺寸居中、等比例留边、铺满裁剪；4:3 素材的后两档目标相同。动画为 24 步，等待整帧写入及显示确认，原图由 SDRAM 缓存供给，不在每个步骤重读 TF 卡。

`src/user_source/hdl_source` 保存相对 `zoom_black2` 有变更的 8 个自研 RTL 文件，目录对应本地工程路径；这些文件不是完整 TD 工程。`sim` 保留针对缓存、行校验、动画和 DMA 的测试台及脚本；需要本地完整工程中的厂商 FIFO、其他原有 RTL 和工具。`evidence` 是当时仿真日志、行宽对照结果及完整源码哈希清单，`history` 保存逐阶段说明。

## 板测与诊断历史

1. 初始动画版在静态画面出现噪点。缓存旁路 A 静态干净但无动画，缓存开启 B 静态有噪点且有动画；这缩小了排查范围，不能单凭 A/B 认定唯一根因。
2. 用户选择局部仲裁修复：跟踪旧读请求的实际返回、辅助事务按最多 8 字分包并在列边界分割，限制占用和交接。故障注入证实旧版本在模拟长尾返回时存在提早交接缺口，但不证明它是所有板端噪点的唯一原因。
3. 用户报告 240×360、240×361 动画无噪点，241×360、241×361 有噪点，原 321×481 动画亦有噪点；两种宽度的 72 动画帧理想存储逐像素仿真均通过，真实硬件差异尚待定位。
4. 在整行写入与读返回之间增加旋转异或签名，241 宽问题视频的诊断显示首次不一致行为 0。校验碰撞可能漏报，也不能区分写入、存储、读取或采样时序。另一行尾诊断版本已生成但没有明确板测结果；当前工程已恢复到整行校验版。
5. 四张新制作对比图曾在板上黑屏；实际 BMP 在连续扇区模型下解析通过，但卡的实际扫描/布局原因未确认。用户决定继续使用先前通过的官方水果图。
6. 用户最终反馈 `ZOOM_CACHE_CHECK_20261029.bit` 所测缩放正常。对应 bit 的 SHA256、时序、验证及本地路径见 [versions.json](versions.json)；请区分这项反馈与历史奇数宽问题。

## 验证范围

行签名单比特故障注入、缓存最大 1024×1024、241×360 一次完整 24 步动画及逐像素显示模型测试通过。最终原构建 setup +0.133ns、hold +0.019ns，STA 覆盖 95.01%。继承的 SDRAM 相关时钟例外仍存在，不能据此称接口电气时序完全闭合；厂商物理 SDRAM 仿真模型为空壳，相关厂商控制器测试不能验证实际读回数据。行签名可以碰撞，零错误标志不保证全部数据正确。

本仓库不包含完整厂商工程、加密 IP、bitstream 或生成的 TD 数据库。可在本地 `archives/20261029_ZOOM_ANIMATION_BOARD_TEST` 找到含完整 user_source、工程描述和已测 bit 的归档（含厂商依赖，工具/许可另备）。其中 bit 已逐字哈希验证，重新构建 bit 哈希不同，不能当成同一份板测文件。

历史说明中的路径以本地 `zoom_animation` 工程根目录为准，其结论保留原时间语境；本页和 versions.json 是当前状态入口。
